Reconcile Mode

{{ if eq .CRD.Mode "typed" }}

This CRD runs in typed mode. Inrun decodes each custom resource into a concrete Go type before reconciliation. Type-safe field access is available to reconcile hooks, enabling precise validation, defaults, and business logic without stringly-typed map lookups.

{{ if .HasAutoscaler }}

This operator uses the Generic Reconciler with reconcile hooks (ReconcileHooks). The hooks receive a fully typed object and can read or modify fields directly. The Generic Reconciler handles the full CR lifecycle — finalizers, managed labels, events, metrics, and health reporting — while hooks provide the business logic for each lifecycle phase.

{{ else }}

The reconcile implementation is provided by a custom constructor. The constructor returns a fully custom reconciler that owns the entire CR lifecycle. Finalizers, events, and metrics are the constructor's responsibility.

{{ end }} {{ else if eq .CRD.Mode "dynamic" }}

This CRD runs in dynamic mode. Inrun works directly with the raw unstructured Kubernetes object — no Go code is required. Reconcile logic is expressed declaratively in the Catalog YAML using template expressions like {{ "{{ .spec.field }}" }}.

The Generic Reconciler manages the full CR lifecycle: it ensures managed labels are set on every reconcile, adds and removes finalizers, runs onCreate and onReconcile template blocks, emits events, increments metrics, and reports health status.

{{ else }}

Reconcile mode unavailable — endpoints are disabled for this CRD.

{{ end }}

Configuration

The operator maintains {{ .CRD.Workers }} worker goroutines {{ if .HasAutoscaler }}(autoscaled, currently {{ .CRD.AutoscalerWorkers.Effective }} effective){{ end }} to process reconcile events concurrently. Each worker dequeues one CR key at a time, reconciles it, and returns. The queue has a maximum depth of {{ .CRD.MaxDepth }} events.

Inrun resyncs all managed resources every {{ .CRD.Resync }} by re-enqueueing every CR key. This ensures drift caused by external changes is corrected even without a Kubernetes watch event.

{{ if .HasAutoscaler }}

Autoscaler

The worker count is managed dynamically. The autoscaler monitors queue depth and adjusts the number of active workers between {{ .CRD.AutoscalerWorkers.Configured }} (configured) and {{ .CRD.AutoscalerWorkers.Max }} (max). At the time of this page load, {{ .CRD.AutoscalerWorkers.InFlight }} reconciles are in-flight and workers are {{ printf "%.0f" .CRD.AutoscalerWorkers.BusyPercent }}% busy.
